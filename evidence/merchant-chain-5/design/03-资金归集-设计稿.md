# 分账合规设计稿 · 之三：资金归集

> 性质=**设计稿，不落码**（老板本人过目后才许落码）｜ 起草=产品侧+A 窗｜ 2026-10-07。
> **总闸（本件最严）**：资金归集在支付行业=「大商户模式/二清」高危区——系统**绝不形成归集账户/资金池**，只做**归集建议报表**（算账 vs 清结算分离的最弱形态）。

## 一、口径（为什么本件只能到「建议报表」为止）

| 形态 | 合规判定 | 本系统取舍 |
|---|---|---|
| 系统内开归集账户，各店收入先入池再分配 | =变相二清，**不可做** | 永不做 |
| 系统指令通道把各店已收款划转总部 | =代扣/清结算，需支付牌照 | 不做 |
| 系统出「各店应归集金额」对账报表，老板线下自转 | =算账，**可做** | **本件只做这个** |

- **归集建议口径**：按日/按店出「可归集余额」=（实收−当日退款−手续费参数−店留运营成本参数），参数全部端口键留口；
- **归集登记**：老板线下转账后回系统登记一笔「归集完成留痕」（金额/日期/凭证号），系统把建议额标记为已归集（对账销号）。

## 二、数据结构（留痕形状，未落码）

### 2.1 归集建议台账 `chain_pool_suggestions`（台账，只增不改）

| 列 | 型 | 说明 |
|---|---|---|
| id | ULID | 单号 `PL-yyyymmdd-店序` |
| biz_date | date | 建议日 |
| store_id | text | 被归集店 |
| received_fen | int | 当日实收（computeDayTender 同源） |
| refund_fen | int | 当日退款 |
| fee_fen | int | 手续费参数扣减（`chain_pool_fee_bp` 缺省 0） |
| keep_fen | int | 店留运营参数（`chain_pool_keep_fen` 缺省 0） |
| suggest_fen | int | 建议归集额=received−refund−fee−keep（负=0 并注记） |
| status | text | `open` → `pooled`（归集登记销号） |
| created_at/updated_at | ts | 审计列 |

### 2.2 归集登记 `chain_pool_records`（留痕）

`{ id, store_id, amount_fen, transferred_at, voucher_no, note, by, created_at }`——手工登记；登记后按金额从旧到新销号 suggestions（FIFO，留销号链）。

## 三、报表形状

- 老板端：三店「可归集余额」卡（Σopen suggestions）+ 归集流水表 + 月度归集率（Σpooled/Σsuggested）；
- 对账钉：Σreceived=日结实收同值（computeDayTender 同源）。

## 四、合规红线（最严，写死）

1. **永不出现**「归集账户/资金池余额」字段——台账只有建议额与登记额，无账户概念；
2. 零支付通道写（e2e 断言零 pay_orders/payments 新行）；
3. 文案全域禁「自动归集/自动划转/代扣」字样（端口键自查+e2e grep 闸）；
4. 若未来接真通道=**另行立项+支付牌照合规评审**，本件永不升级。
