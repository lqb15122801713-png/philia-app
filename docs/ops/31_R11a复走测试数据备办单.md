## 二、件 4 注入实证专项（八件唯一硬点）

1. **为什么必须注入**：回馈金「统一次月到账」（CJ-0922-13②）——当月任何消费只挂期次、不进可用余额；有效期 365 天——临期件只能靠有效期回填。自然路径两者都造不出。
2. **注入纪律**：
   - 走「注入实证」机制（军规口径：定时器/长周期类=监理代码级核查+产品侧注入实证，QA 不背）；
   - 只造 rebate 域测试行（rebate_accounts 余额 + rebate_logs 发放类流水：前后余额+单号+期次齐全），**不动已收/不动储值/不动 XP**——注入不是动账；
   - 注入流水单号统一 `INJECT-` 前缀 + 测试手机号段统一报备，防与真实会员混淆；
   - 注入件清单同步监理 B 窗，复走后由 B 窗核消确认。
3. **处置口径（老板已拍，CJ-0923-13）**：复走后注入件**保留留痕标测试件不删**（与三笔 5 星假评价保留先例 CJ-0922-10① 同轨）。

### 6.1 设计依据（schema+代码实证核对，非拍脑袋）

已逐行核对 `server/drizzle/0015_unusual_ares.sql` + `server/src/services/rebate.ts` + `server/src/routers/membership.ts`：

1. **rebate_logs 无独立有效期列**——有效期=发放/入账时间 + `rebate_validity_days`（读表默认 365，plans 端点透出）→ **临期笔=入账时间回填**（2025-10-05 入账 → 2026-10-05 到期，距今 12 天=临期 ✓）。
2. **已到账余额**=rebate_accounts.balance_fen + 入账行 settlement_id 非空——注入行**必须回标 settlement_id**，否则被 settleMonthly 未来结算扫入双入账、且误入「本期预计」（balanceOf 的 pendingFen=settlement_id IS NULL 的 grant 合计）。
3. **明细可见性**：my 端点「本期明细」=当期 period 过滤（rebatePeriodOf：9-23 → '2026-09'）——注入流水 period 标当期 '2026-09' **仅为页面可见性**（测试件对真实期次的刻意偏离，批次单行保留真实期次，B 窗按 INJECT- 前缀核消即可识别）。
4. **会员实例**：memberships 行照 sell 端点同构（plan_key='plan_yinghuo'/sold_store=首店/started=now−30d/expires=now+335d/status='active'/paid_fen=19900）；users 旁路建档同构（kimi_id='phone:<手机号>'，nickname+user_roles customer）。
5. **幂等**：全量 `INSERT OR IGNORE`，重跑零副作用。
