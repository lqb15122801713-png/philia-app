## 一、总纲一句话

**机制定死、策略配置化**——系统只提供机制（权限点/审批流/配置体系），不替老板规定策略（阈值/文案/分值/玩法）；策略全部后台可配，老板后期自己裁决。与老板纲领（CJ-0923-16/17）完全一致，且业界有成熟实现（Toast/Square/Shopify/银豹/美团/Salesforce 互证）。

## 二、三端权限模型（标杆实证）

1. **没有标杆把「店员/店长/店主」写成三个死枚举**。通行模式=**权限点目录 → 角色模板（RBAC）→ 逐人覆写 + 门店维度数据隔离**（Square：A 店员工看不到 B 店数据——我们三店直接抄）。
2. **权限点驱动，不绑角色名**：组件绑 `order:refund` 权限点，不绑「店长/老板」名单——否则新增角色要改上百处代码。
3. **权限调整全部放后台**：老板端角色编辑器（勾选权限点+调阈值数值）；开发只维护权限点目录。防提权护栏：只能授予自己拥有的权限（Toast）；角色 level 序（低不能改高）；修改须交接班重登生效（银豹，防营业中途权限漂移）；内置角色不可删（美团）。
4. **「同一屏三种视界」=四层实现**：动态路由（按权限滤菜单）→ 按钮级指令（无权限移除 DOM）→ 字段级条件渲染（表格列）→ **数据级遮蔽**（店员不见营业额=数据不出接口，不是隐藏样式）+ **后端必须兜底**（前端显隐只是体验，接口按角色硬拒，防共享平板绕过）。

## 三、敏感动作的三层设计（Y5 的标准答案）

业界对敏感动作（退款/改价/免单/反结账）不做硬拒、也不做自由放行，做**三层叠加**：

1. **权限开关**（能不能做——权限点）；
2. **数值阈值**（做到什么程度——后台可配数值：折扣上限/退款阈值/减免限额，多阈值命中取最严）；
3. **审批升级**（超额怎么办——**Approval required 第三态**（Shopify POS 实证）：触发后须另一名有权的员工/店长/店主现场批准，责任人=审批人而非操作人）。

配套：强制原因+全留痕不可改（申请人/审批人/金额/原因/前后值/设备/时间）；反结账权限等级>普通退款（套现第一漏洞，银豹甚至单列「已交接班单据可否反结账」开关）。

**→ Y5 正解**：超阈值退款既不该硬拒（现状错），也不该直接放行，而应**落「待审批」**（第三态）——**机制（三态+审批流状态机+留痕）现在定死建好；策略（¥500 阈值、谁批、店长能否驳回）全部端口化，老板后期裁决**。驳回权（CJ-0922-08）由此自然有单可驳，且不动 R12 已冻结的钱口径（六联动同事务不变，变的只是入口落单态）。

## 四、配置化边界（可配/慎配/不可配）

| 类 | 项 | 护栏 |
|---|---|---|
| **可配**（直接开放） | 价格/折扣规则/积分分值/税率/服务费/文案/图片/营销位/流程开关/角色权限矩阵 | 配置草稿→统一发布→版本回溯 |
| **慎配**（留口+护栏） | 退款规则/折扣上限/经营参数（分摊比例/结算周期）/非原路退款 | 独立权限点+审批流+数值边界校验+全量审计+涉钱双人复核 |
| **不可配**（只能发版） | 核心账务口径（记账/结算/对账/舍入）/支付路由/安全策略（加密鉴权风控核心）/审计链/schema 结构 | 改动=代码评审+测试+发版；审计日志禁 UPDATE/DELETE（可配的审计不是审计） |

**留口安全的四个机制**：
1. **发布模型**（Toast Change sets）：配置改动先入草稿，统一「发布」才下发三端——门店看到的永远是一致快照；
2. **快照落单**：交易凭证类文案/价格按下单时版本存档，不查时现取（客诉可还原当时承诺）；
3. **涉钱配置**：审批+留痕+（必要时）次日生效；
4. **配置缓存**：变更推送+兜底 TTL，防「价格已改、文案还旧」的一致性窗口。

## 五、定死 vs 后期管理（边界表）

| 现在定死（机制层，改动=返工） | 后期管理（策略层，后台可调） |
|---|---|
| 数据模型/表结构 | 折扣力度/分值/会员人数目标 |
| 钱口径（记账/结算/对账/舍入/三本账） | 营销活动/活动规则/促销玩法 |
| 权限模型（权限点目录/RBAC/角色边界） | 阈值参数（退款阈值/上限/频控/有效期） |
| **审批流机制（三态+状态机+留痕）** | **谁审/多少额/什么时候批** |
| 安全（支付/PII/加密/审计链） | 文案/话术/通知模板 |
| 接口契约/事件 schema | 视觉样式/主题皮肤 |
| 配置体系与发布机制本身 | 开关状态/灰度范围/活动排期 |

口诀：**变化频繁且归业务方所有→配置/规则外置；改动要全系统重测→锁死**（Moore core/context、Unix 机制与策略分离、BRMS 业务规则外置、Brooks 数据结构是心脏——四源互证）。

## 七、切换日 cutover 清单（业界硬规矩）

1. Runbook 逐步写责任人与预估时长，演练后修订；
2. **全流程演练 ≥2 次，至少 1 次含故意回滚**；用全量生产级数据（导演雷法同源）；
3. **Go/No-Go 用客观阈值**（对账差异 %/错误率），事先定谁有权喊停（=老板）；
4. 冻结窗口+增量 delta 捕获，杜绝幽灵行；
5. 回滚预案写明「不可返回点」——**回滚路径没实测过等于没有**；
6. 对账不止行数：键/关系/关键业务查询，差异须可解释；
7. **双轨期=并行运行至连续两个结账周期全绿**才退役旧系统（餐饮/活体/转诊/记账本/渠道等老系统续跑域照此，接 D-11）；
8. 避开旺季前一周上线；war room 状态页按时间戳播报。

## 八、Philia 立即修正清单（学习结论落项目）

1. **权限点目录先行**（含次卡核销/积分调整/提成修改/退款/改价/免单/反结账/端口管理/数据导出）→三端默认角色模板→老板端角色编辑器（控制台端口批承载；权限矩阵 V1.3=模板 V1）。
2. **敏感动作三态化**（允许/拒绝/需审批）+阈值端口化——修复包「驳回权放开店长」施工口径修订为：**超阈值=落 draft 待批（第三态），阈值数值与驳回角色=端口**（机制定死，策略留口；Y5 正解，R12 钱口径不动）。
3. **配置发布机制**：控制台端口批加「配置草稿→统一发布→版本回溯+快照落单」（与 18 号档五层防护 L3 三段式发布同源）。
4. **切换日执行包补四件**：G4 试点店（贝肯山先行）/G5 波次预案/G7 hypercare 两周/演练≥2 次含故意回滚+Go-NoGo 阈值+双轨两个结账周期。
5. **文案端口**（CJ-0923-16 已立项）按「文案中心 key-value+版本下发+快照落单+合规审核位」实现。
