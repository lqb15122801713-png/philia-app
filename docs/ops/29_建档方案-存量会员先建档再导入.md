## 一、问题定义

储值导入接口（R5b 已交付）按**手机号主键匹配**用户——账面上的人必须先在系统里「存在」（有 users 档案），否则 907 人的 ¥671,264.42 无处落账。建档≠现场注册：批量预建档，客户首登（手机号）即激活并看到迁移过来的余额。

## 二、执行序列（切换日，五步全留痕）

| 步 | 动作 | 通道 | 状态 |
|---|---|---|---|
| 1 | **建档 dry-run（零写入对账报告）**：读台账 CSV → 拟建档 N 人（排除已建档）/三店分布/异常行逐条列出——零写入，运营先核 | 批量建档端点（dry-run 模式）——**待建，进切换日执行包任务书** | 📝通道待建 |
| 2 | **建档执行**：批量创建 users 档案（手机号主键幂等：已存在=跳过标「已存在」）；建档批次号+逐行留痕（谁/何时/台账行号） | 批量建档端点（execute 模式）——**待建，同上** | 📝通道待建 |
| 3 | **储值 preview 对账**：建档后跑 preview——校验位必须与真台账吻合（907 人/¥671,264.42/三店分布/次卡夹带 150） | `storedValue.previewImport`（R5b 既有，零写入） | ✅通道就绪 |
| 4 | **储值导入 execute**：批次留痕+试导可清除（已消费批次拒清） | `storedValue.executeImport`（R5b 既有，仅 owner） | ✅通道就绪 |
| 5 | **复走抽验**：运营按抽验口径逐会员抽核（余额/归属店/次卡）；产品侧出对账比对工具（台账 vs 库内逐人 diff） | 抽验=人工+比对工具（执行包组件） | 📝工具待建 |

**执行前置**：全库备份（DEPLOY §5 停写拷贝 philia.db）+老板书面授权（按按钮=产品侧执行）。

## 三、口径钉死

- **手机号主键**（1286 唯一）：会员编号缺失 344 行不影响（手机号为唯一事实源）；同一手机号多行=同一人，储值按行累加（接口事务内重读账户，R5b 代码实证）。
- **三店归属**：客户档案全局唯一（中央一本账，决策 #41）——门店归属不落 users，落在**储值账户行**（stored_value_accounts.store_id=台账门店列映射）；余额中央通用。
- **次卡夹带 150 人**：R5b 接口仅计数预留（passCarryRows），**本通道不建次卡**——正式映射=旧卡名 8 种→新次卡规格映射表（**运营供**），次卡导入通道待建（进切换日执行包任务书，与储值同序列）。
- **幂等**：建档=手机号查重跳过（不产生双份）；储值 execute **无文件级幂等**（R5b 代码实证：重复 execute 会重复入账）——纪律=正式导入一次性执行，试导走 clearImportBatch 清除后重导。
- **防假**：任何一步校验位与台账不合=停，不许「差不多就导」。
- 建档**静默**：不触发任何通知/营销动作，首登才激活感知。

## 四、与会员体系（R11a 已上线）的关系

建档出来的客户默认**非会员**（无档位）；微光档=客户首登后自助一键开（R11a 已上线）；存量付费会员识别=台账若有会员标记列则标，无则切换日后运营逐批补录（**待运营确认台账是否有会员档位列**——若无，切换日只迁储值/次卡，档位由到店首单时店员协助开通）。

## 五、字段级映射表（V1.0 补齐件①）

### 5.1 台账 CSV 实读列（以 R5b 接口 LEDGER_COLUMNS 代码实证为准）

接口按**表头名**定位（列序错位容错）；必要列缺列=整单拒绝不猜列序。实读 9 列，其余列不读不入库（留 CSV 存档备查）：

| 台账列名 | 系统落点 | 转换规则 |
|---|---|---|
| 门店 | 储值账户 store_id | 入参 mapping {台账店名: storeId}（贝肯山店/生活馆店/生态城店三行映射，未映射行失败留痕） |
| 会员编号 | **不入库** | 344 行缺失，不作主键；编号留 CSV 存档 |
| 会员姓名 | users.nickname（建档时） | 空则落「新客 <手机号尾 4 位>」（同 membership.sell 旁路建档口径） |
| 手机号码 | **users.phone（主键）** | 建档：查无则建（kimi_id='phone:<手机号>'，user_roles+customer）；导入：查无则失败留痕「会员未建档」 |
| 会员卡名称 | 不入库 | 旧卡体系随储值转型作废（新售冻结） |
| 储值本金余额(¥) | stored_value_accounts.principal_fen | 元→分两位小数；容错 ¥/￥/千分位/空白（空=0）；负数/非法=失败行 |
| 储值赠送金额(¥) | stored_value_accounts.bonus_fen | 同上；本金/赠送分列（账目四分列口径） |
| 次卡名称 | 预留（passCarryRows 计数） | 映射表待运营供；导入通道待建 |
| 次卡剩余次数 | 预留（同上） | 同上 |

### 5.2 建档写入（待建端点字段级规格）

| 系统字段 | 取值 | 说明 |
|---|---|---|
| users.id | 系统生成 | 文本主键 |
| users.kimi_id | `phone:<手机号>` | 旁路建档占位（同 sell 端点先例） |
| users.nickname | 会员姓名 / 「新客 尾 4 位」 | — |
| users.phone | 手机号码 | 主键幂等键（**注意：schema 层 phone 无唯一索引，唯一性=应用层口径**——见 §十一 风险②） |
| user_roles | customer | 一人一行 |
| 建档批次留痕 | 批次号+台账行号+操作人+时间 | 逐行可查（批次表随执行包任务书定稿） |

## 六、异常行处置细则（V1.0 补齐件②）

**总原则：异常行零写入+逐条留痕（行号+原因）+回运营核对，不猜不改台账。**

| 异常 | 触发 | 处置 |
|---|---|---|
| 手机号缺失/非法 | 非 1 开头 11 位 | 不建档不导入；列异常清单回运营补录后随补录批再跑 |
| 手机号重复（1290 行/1286 唯一） | 同号多行 | 正常情形=同一人多笔台账：建档一次，储值按行累加；dry-run 报告列「合并人数 4」供运营核 |
| 会员编号缺失 344 行 | 编号列空 | 不影响（编号不作主键），报告计数留痕 |
| 门店未映射 | mapping 缺该店名 | 行失败留痕；三行映射是必填前置，dry-run 先炸出来 |
| 会员未建档 | 储值导入时查无 users 行 | 建档先行的意义所在；preview 阶段此原因应=0，>0 即停 |
| 金额列非法 | 本金/赠送非 ≥0 数字 | 行失败留痕回运营 |
| 库内手机号已存在 | 建档查重命中 | 跳过标「已存在」——**但若命中的是测试号/演示号占了真实客户手机号=红色异常**（见 §十一 风险②） |

## 九、回滚预案（V1.0 补齐件⑤）

1. **总闸**：切换日执行前全库备份（DEPLOY §5：停写→拷贝 philia.db→启）；任何一步校验位不合=停，必要时恢复备份重来。
2. **储值回滚**：`clearImportBatch` 既有——删批次流水+反向冲减账户+空账户清理，批次行永存留痕；**已消费批次拒清**（差错走对账调整留痕，不删账）。
3. **建档回滚**：按建档批次号删除该批 users（**仅限未产生任何业务行的档案**——已消费/已开档/已预约的拒删，走人工对账）；建档回滚端点待建（进切换日执行包任务书）。
4. **次卡回滚**：随次卡导入通道任务书同规格设计（批次留痕+可清除+已核销拒清）。

## 十一、自检记录（军规二）+ 反对意见与风险（军规一）

**自检**：
- Loop 1：V0.5 五件补齐件逐项落——映射表✓（§五，列名以 R5b 代码 LEDGER_COLUMNS 实证非记忆）/异常细则✓（§六）/界面稿✓（§七骨架级）/验收用例✓（§八 8 条）/回滚✓（§九）；
- Loop 2：①校验位七项与台账实证数字回对（1290/907/¥671,264.42/1286/728·328·234/150/344）✓；②execute 幂等口径更正——V0.5 写「导入可重跑不产生双份」，代码实证 executeImport **无文件级幂等**（重复 execute 重复入账），已改为「一次性执行+试导走清除重导」纪律（§三）✓；③门店归属落点核实——users 无门店列，归属落储值账户行（§三）✓。
- **残留风险**：①次卡通道未建，150 人的次卡是切换日最大开口项——依赖运营映射表+执行包施工；②**users.phone 无 schema 级唯一索引**（唯一性=应用层口径）——建档端点施工时须加查重硬闸，dry-run 报告必须列「库内已存在」明细防测试号占真号；③首登激活体验依赖 dev-login/正式登录通道口径，切换日前需实测。

**反对意见与风险**：
1. **静默建档的信任风险**：不通知=客户首登才发现余额——若迁移数据有错，是客户先发现而不是我们，对「制度级透明」定位是反噬。对策：切换日后 48h 内运营完成抽验+备好客服话术（余额异议一键查导入批次留痕）；建议切换日后一周内店内向存量会员主动告知「余额已迁入新系统可查」——告知动作归运营定。
2. **execute 无幂等是真实雷区**：切换日现场若网络抖动重点一次=67 万翻倍。已用纪律（一次性执行+校验位全绿才可点）兜底，但建议执行包任务书给 executeImport 补**文件指纹幂等**（同 CSV 指纹拒重入）——施工时评估，半件小工。
3. **会员档位列缺口**：若台账无会员标记列，存量付费会员（如有）的档位只能切换日后人工补录——期间这些客户到店无档位权益，需门店话术兜底（运营备）。

> 下一棒：运营过稿（攻防口径：台账核对+次卡映射表+会员档位列确认）→ 修订 → 切换日执行包任务书收编（含建档/次卡/比对工具三件通道施工）。
