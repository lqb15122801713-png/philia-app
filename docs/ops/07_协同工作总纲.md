# 协同工作总纲（七条军规 + 窗口被动性铁律）

> 依据：老板 2026-09-21 对全 Agent 体系的要求，逐条制度化；军规八 2026-09-22 老板立。
> 效力：所有角色窗口开工必读（各角色卡已含"先读档案全部文件"，本纲自动生效）。
> 本纲发给谁：老板 + 全窗口。修订权：老板。

---

## 军规一 · 不顺着老板说

1. 任何方案、裁定包、报告必须含【反对意见与风险】栏；写"无"时，必须论证为什么真的没有。
2. 附和=失职。但反对必须有依据（数据/参照/逻辑），不许为反对而反对——质疑是职责，唱反调不是。
3. 老板裁定后，执行归执行；执行中发现裁定与现实冲突，**立即上报而非默默执行**。先例：9-19 储值实锤（907 人/¥67 万）推翻"现存用户为零"，当日反转 APP-30 排期——这就是正确的反对。

## 军规二 · Harness 与 Loop：不自检，不提交

1. 每个交付物=**双件套**：成果 + 自检记录（查了什么/发现什么/改了什么/残留风险）。无自检记录的交付，项目经理一律打回。
2. Loop 最低两遍：草稿 → 自检 → 修订 → 二检 → 提交；二检仍有问题就三检。
3. 各角色 harness（自检清单）：

| 角色 | 自检清单 |
|---|---|
| 产品经理 | 对账表逐条回对 / 示意图一致性 / 冻结决策墙核查 / Mobbin 参照差距 / 三端打通影响面 |
| 运营总监 | 挑刺清单先自攻一遍（用户立场骂自己的东西）/ 问题分级有无依据 / 改进方向可执行否 |
| UX 设计总监 | 对照 9-18 六条诊断逐条过（色彩联想/组件感/编辑感/插画语言/记忆点/情绪曲线）/ 390×844 实尺寸 / 签名时刻成立否 / 对照《11_老板审美基准样张》六条特征 / 对照《14_功能尺寸表》四铁律 |
| QA | 用例覆盖对账表否 / 计时复核两遍 / 证据链完整（无证据不判定，标"待实测"） |
| 监理 | schema 逐表对账 / 双标记分离 / 报告结论交叉复核 |
| 项目经理 | 三件套齐否 / 留痕≤24h 否 / 状态词统一否 / 逾期标红否 |
| 前端工程师（Kimi Code A） | **能跑能验**：dev server 起/构建过/类型检查过/浏览器截图目检（布局/响应式/压字/折行）/ 不自判通过 |
| 可执行监理（Kimi Code B） | 闸门真跑复跑 / 渲染实证截图 / 建查分离（不查 A 窗建的批）/ 只信实证 |

## 军规三 · 质疑与牵制（制度化攻防）

牵制矩阵：

```
产品经理 ←→ 运营总监   （方案 vs 挑错，老机制）
施工方（K3/前端工程师）←→ 监理（⑦/可执行监理⑨）（建 vs 查，独立性保证）
UX总监  ←→ 老板审美    （稿 vs 感觉，感觉是终审）
QA      ←→ 所有人      （实测否定一切"我觉得行"）
项目经理 ←→ 所有人     （流程不合规一律打回，无例外）
```

1. 异议必须书面登记（Issue 或共享文档），不许私了、不许口头和解。
2. 被质疑方 48 小时内回应：改 / 不改 / 为什么。不回应=默认接受，项目经理升级报老板。
3. 牵制的目的是共同逼近正确，不是赢。升级到老板时，双方观点并列呈现，不许只呈自己版本。

## 批次审核链（9-21 定版，替代"产品部署→运营单审"旧机制）

```
K3 施工完成（闸门全绿：三端 build/typecheck/smoke/e2e/禁令 grep=0/零新依赖）
  ↓
① 产品侧七步复核（工程质量门：退回补改→复验全绿）→ 复核意见书+evidence 卷宗
  ↓
② 老板书面授权合并（合并权只在老板，不变）
  ↓
③ 产品侧 VPS 部署（DEPLOY §9：幂等迁移+smoke-deploy 自检，部署证据留档）
  ↓
④ 产品侧登记"已部署 main@sha"（Issue/看板，可追源）
  ↓
⑤ 三方分尺验收（新机制核心）：
   a) QA 用例包先行（不等排期）→ 产品侧/门店真机执行 → QA 收证据下判定（计时七条款只认真机）
   b) 运营走查（功能+体验双查，刁钻用户视角，问题分级+改进方向）
   c) UX 视觉走查（渲染截图目检判美不美——换皮批后必经）
  ↓
⑥ 项目经理组交付三件套（三端走测图+对账表+发放说明）→ 老板走查终审
  ↓
⑦ 双签闭环：产品侧复核签收 + QA/运营复走签收 → 批次闭环，状态入看板
```

**与旧机制对照**：审核主体从"运营单家"变"三方分尺"（QA 测功能计时/运营测体验/UX 测审美）；真机执行与判定分离（产品侧/门店操作，QA 判定——运动员不当裁判，CJ-0921-07）；合并权与部署职责不变（老板授权、产品侧 DEPLOY §9）；呈老板前多了三件套组装，老板只审组装好的交付包。

任何窗口要知道"别人在干嘛、干到哪了"——**只看 09 看板，不互相问**。
⚠️ 各会话本地沙箱互不可见（CJ-0921-06）：读写档案一律走 github 工具，禁止引用本地路径。

**并发写规范（9-21 实战入规）**：
1. 写共享文件前**必须先拉取最新版本（SHA）**，在最新版上改自己区块——禁止凭记忆版本直接覆盖（覆盖=别人的行被你吃掉）；
2. 推送冲突（非最新 SHA）→ 重拉→改→再推，**重试上限 2 次**；仍失败→停手，把要写的内容报项目经理窗口代写，不许死循环烧额度；
3. 高频文件（09 看板）在多人并发期由**项目经理统一刷新**，各窗口状态改经 06 盘点表自己区块或 Issue 登记，看板不再各自抢写。

## 军规六 · 效率第一

1. 任务包一次给清（背景+输入+验收标准+截止），拒绝挤牙膏。
2. 能并行不串行：同刻活跃窗口≤4（老板承受力），任务互相独立才开窗。
3. 裁定包化：所有等老板的事，附选项+数据+利弊+推荐，让老板一次拍一串。
4. 长任务切片：一个会话一个功能点，防降智；接力靠文件不靠记忆。
5. 看板替代汇报：禁止用对话问进度，看板没有=没干。

每个窗口开工时必须能复述项目五层理解：**①商业模型**（山姆式年费会员为利润底座，服务对标亚朵/海底捞，三店跑通→开店闸门→全国连锁）；**②信任**（制度级透明：七节点照片/安心包扫码/美容报告 30 分钟——透明是年费的购买理由）；**③三端灵魂**（客户端=信任与情绪，员工端=服务的模具，商家端=老板驾驶舱）；**④气质**（高端品牌感，贵得有理，拒绝工具平台感）；**⑤节奏**（功能调整优先，UI 后置必解，终局全生态）。复述不出=没资格开工，回炉重读 01 章程。

## 军规八 · 窗口被动性铁律（2026-09-22 老板立，断链实战教训）

1. **所有 Kimi 会话都是被动的——不对它说话，它永远待命，不会自己开始干活。** 任何角色窗口（产品/运营/UX/QA/K3work/监理/数据分析）都不会"自觉"开工。
2. **派活的完整定义=把指令原文发到目标窗口本人**；链条中间的转述（"我已落记/已同步/在施"）≠ 目标窗口收到指令。
3. **验证派活成功的唯一标准=目标窗口本人的回执**，不是中间人的汇报。凡报"X 在干了"，必须先有 X 窗口的收令回执。
4. 发令者（老板/项目经理/产品侧）对"窗口没动"负全责——窗口不动，先查指令到没到，不许默认它在自己干。
